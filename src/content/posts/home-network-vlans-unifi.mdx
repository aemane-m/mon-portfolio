A homelab quickly stops being "a few machines on the home network". Once photos, home automation and backups live on hardware I own, I want to control **who can talk to what**. This article explains how I built my local network around that idea, with UniFi equipment and separate VLANs.

<Callout tone="brand">I am a learner, not a network engineer. I describe what I built and what went wrong, not a reference design.</Callout>

## Why separate networks

A flat network treats a smart plug, a laptop and a server as equals. They are not. A cheap IoT device that is never updated should not be able to reach the machine that holds my photos. Splitting the network into **VLANs** gives each kind of device its own space, and puts the gateway in the middle, so every crossing between spaces becomes a rule I decide.

## What the gateway does for the homelab

The gateway is more than a router for me. It is also the **DNS resolver** (so my services have friendly names), the **DHCP server** (with reservations for the virtual machines that need a stable address), and the peer that my Kubernetes cluster talks to: the cluster announces the address of its entry point to the gateway using BGP, so a service in the cluster is reachable from the rest of the network like any other.

## Putting Proxmox on a VLAN: the mistake that cost me an evening

My Proxmox hosts are plugged into a switch port that already belongs to the Servers VLAN. The VLAN is applied by the switch, and the traffic arrives untagged on the host.

I then also told Terraform to tag every virtual machine with the same VLAN. The result: **no virtual machine received an address**. The VLAN was being applied twice. The rule I now follow is to choose **one** place to tag:

- If the switch port is an *access* port in the VLAN, the virtual machines must **not** carry a tag.
- A tag on the hypervisor side only makes sense when the bridge is connected to a *trunk*.

## Stable addresses without chaos

Not every machine gets the same treatment. The Kubernetes nodes use **static addresses**, because control-plane nodes must be predictable. Other virtual machines get a **DHCP reservation** on the gateway, which keeps one source of truth for addresses without configuring each machine by hand.

## Isolation: zones and an explicit allow-list

VLANs separate the networks. What decides who can talk to whom is the **firewall**, and I use UniFi's zone-based model: networks are grouped into **zones**, and traffic between zones is blocked unless a rule allows it.

The default stance is the one that matters: **everything between zones is blocked, except what I explicitly allow.** Over time I wrote a short list of rules, each named after its purpose:

      ["My workstation can reach the Management zone", "I administer the network and the servers from one machine, not from everywhere"],
      ["The first Proxmox node can reach the iLO and one management Mac", "The nightly backup script needs to power the NAS on and reach a backup target — and nothing else on the Servers network needs that access"],
      ["Internal can reach Untrusted", "I can control or check my IoT devices from my side"],
      ["The management Mac can reach Internal and Untrusted", "It is the one machine allowed to look at both sides"],
      ["mDNS is allowed to the gateway", "So that devices on different networks can still discover each other"]
    ]
  }}
/>

Two things I like about this approach. First, **the rules describe intent**: each one is named after what it is for, so six months later I can still tell why it exists. Second, **the management interfaces are not reachable from the whole network**. The server's remote-management port (iLO) can power a machine on and open a console, which is exactly why very few things should be able to talk to it.

<Callout tone="neutral">Isolation is a set of rules, not a label. A VLAN on its own separates broadcast traffic; it is the firewall rules between networks that decide what can actually cross.</Callout>

## What I would improve

I treat the network configuration as the one part of my homelab that is not yet described as code: it lives in the UniFi controller, and my repository depends on it (for example for DNS entries). Bringing it under version control is on my list.
